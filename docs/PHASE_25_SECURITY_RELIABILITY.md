# Phase 25 — Security, Reliability and Error Handling

## Objective

Harden the complete system without expanding its documented scope.

## Implemented

### Authentication

- Administrator-only API access remains enforced through DRF permissions.
- Login accepts username/email and rejects inactive or non-staff users.
- Login is rate-limited to 5 attempts per minute per throttle scope.
- Successful login rotates the administrator's API token.
- Logout invalidates the current token.
- Frontend tokens remain in `sessionStorage`, not persistent local storage.
- Frontend clears its authenticated session when the API returns HTTP 401.

### Authorization

- Protected endpoints use `IsAdminUser`.
- Faults are generated by the monitoring/fault-detection layer and can no longer be created directly through the public API.
- Fault acknowledgement and resolution remain explicit authenticated actions.

### Input validation

- Device IP addresses are IPv4 validated.
- Device types and fault states use enumerated choices.
- Monitoring intervals have a minimum of 5 seconds.
- SNMP ports are restricted to 1–65535.
- SNMP timeouts are bounded between 0.1 and 30 seconds.
- SNMP versions are restricted to v1/v2c.
- Device names cannot be blank.

### Sensitive configuration

- `DJANGO_SECRET_KEY` is required outside the test environment.
- The previous development fallback secret was removed.
- `.env.example` contains placeholders only.
- SNMP community values remain write-only at the API serializer boundary.
- Real environment secrets must not be committed to Git.

### CORS / CSRF / tokens

- CORS is explicit and does not allow `*`.
- CSRF middleware remains enabled for Django/session-protected paths.
- API authentication uses DRF token authentication through the `Authorization` header.
- Token-authenticated API requests do not depend on a CSRF cookie.
- Secure cookie and HTTPS settings remain configurable for deployment.

### Redis / Celery reliability

- Monitoring tasks already isolate ICMP and SNMP failures.
- Redis lock failures now return an explicit `dependency_error` result instead of being confused with a device monitoring failure.
- Redis lock release failures are logged without masking the monitoring result.
- Existing distributed locking prevents overlapping monitoring runs.

### Database integrity

- Active/acknowledged fault uniqueness remains enforced at the database level.
- Regression tests verify duplicate active fault types cannot be inserted for the same device.
- Existing foreign keys, one-to-one relationships, indexes and constraints remain intact.

### Frontend API error handling

- Network failures produce a user-safe error.
- Non-2xx responses become structured `ApiError` instances.
- HTTP 401 clears the stored token and emits an authentication-expired event.
- The auth provider converts that event into a signed-out frontend state.
- Backend error details are not rendered as raw server stack traces by the API client.

### Logging

- Monitoring failures use structured log messages and exception traces for server-side diagnostics.
- Client-facing task errors use generic messages where appropriate.
- Sensitive SNMP credentials are not returned by the configuration API.

## Validation matrix

| Area | Validation | Evidence |
|---|---|---|
| Authentication | Anonymous access rejected; non-staff rejected; login rate limited; token rotation verified | `network/test_security.py` |
| Authorization | Fault creation blocked; protected APIs require admin | `network/test_security.py` |
| Input validation | Invalid device and monitoring configuration values rejected | `network/test_security.py` + serializer tests |
| Sensitive configuration | Secret fallback removed; SNMP community hidden from responses | settings + security tests |
| CORS | Explicit origins only; wildcard rejected | security test |
| CSRF/token behavior | CSRF middleware enabled; API uses token header authentication | settings + authentication tests |
| Redis/Celery | Redis lock outage returns dependency error | `network/test_security.py` |
| Database integrity | Duplicate active fault prevented | `network/test_security.py` |
| Frontend auth errors | HTTP 401 clears token/session | `frontend/src/api/client.ts`, `frontend/src/auth/AuthProvider.tsx` |
| Production configuration | `DEBUG=False` by default; deployment secret required | settings + deployment checks |

## Required local verification

Run from `backend/`:

```bash
python manage.py test
python manage.py check --deploy
```

Run from `frontend/`:

```bash
npm run lint
npm run build
```

For a deployment environment, set a real `DJANGO_SECRET_KEY`, explicit `DJANGO_ALLOWED_HOSTS`, explicit `CORS_ALLOWED_ORIGINS`, and the HTTPS/security settings appropriate to the deployment. Do not use the values in `.env.example` as production secrets.

## Scope boundary

This phase does not add new monitoring protocols, external notification providers, MFA, SSO, WAF functionality, or other features outside the documented project scope. It hardens the existing authentication, API, monitoring, persistence, worker, and frontend behavior only.
